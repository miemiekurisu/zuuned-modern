# Getting a Zune onto WinUSB on Windows

Short version: **use Zadig**.  Do not hand-write an INF and do not install the
Zune software - this is a solved problem upstream, and the in-box pieces are not
quite enough on their own.

Nothing in Zuuned installs a driver.  Until a Windows installer exists, binding
is a one-time manual step per machine, done by whoever is testing hardware.

## First, check whether you need any of this

Binding WinUSB buys the ZMDB line, where the app reads the player's own database.  It
is not the only way zuuned reaches a player on Windows.  A player Windows has already
given a driver to - on the development machine, the in-box UMDF MTP driver
`wudfwpdmtp` - is reachable *through that driver*, and zuuned then browses it, sends to
it, reads a file back and deletes one with nothing installed by hand.  That is measured
on one player; `docs/WINDOWS_PORT.md` owns that evidence.

So ask before installing anything, with the player attached:

```
powershell -NoProfile -File packaging\windows\check-driver.ps1
build\devicetool.exe
```

`devicetool` opens nothing and answers for both lines at once.  What its answers mean:

- `os_wpd_interface=1` with `os_driver=wudfwpdmtp` - Windows already hands this player
  to zuuned over MTP.  **Stop here.**  Installing WinUSB over it replaces the driver
  Windows is using now, and nothing in zuuned needs that in order to talk to the player.
- `os_problem=CM_PROB_FAILED_INSTALL`, no driver at all - nothing can reach the player,
  and Route A below is the fix.
- `os_driver=WinUSB` with a device interface GUID - the ZMDB line, which is what the
  rest of this page is about.

`libusb_sighted=1` on its own is not a claim that the app can use the player.  On an
MTP-bound player libusb reads the descriptors and then fails `claim_interface` with
Access denied, because Windows owns the interface; zuuned notices that and takes the MTP
route rather than reporting a dead device.

**Status: run against hardware on 2026-10-20, and it worked.**  A Zune HD on the
development machine went from problem 28 to `CM_PROB_NONE`, is bound to `WinUSB`,
registers an interface GUID, is sighted by libusb, and has been opened and read by
`build\zuuned.exe`.  Both captures are below, before and after, as the script
actually printed them, except for two strings and both of them on purpose: the serial
number in the devnode instance path and the interface GUID Zadig generated appear here
as `<serial>` and `<generated-guid>`, because those two identify one person's player on
one person's machine, and this page ships inside the release archive.  What this page
still does not cover is anything past the library read - that lives in
`docs/WINDOWS_PORT.md`.

## What has to be true afterwards

Both of these, not just the first.  Measured on the development machine with a
Zune HD attached (`check-driver.ps1`), before anything was installed:

```
devnode : USB\VID_045E&PID_063E\<serial>
status  : Error  problem=CM_PROB_FAILED_INSTALL
hwids   : USB\VID_045E&PID_063E&REV_0100 USB\VID_045E&PID_063E
compat  : USB\MS_COMP_MTPZ USB\Class_FF&SubClass_FF&Prot_FF USB\Class_FF&SubClass_FF USB\Class_FF
children: none - single function
```

And after, same script, 2026-10-20:

```
devnode  : USB\VID_045E&PID_063E\<serial>
status   : OK  problem=CM_PROB_NONE
hwids    : USB\VID_045E&PID_063E&REV_0100 USB\VID_045E&PID_063E
compat   : USB\MS_COMP_MTPZ USB\Class_FF&SubClass_FF&Prot_FF USB\Class_FF&SubClass_FF USB\Class_FF
driver   : {88bae032-5a81-49f0-bc3d-a4ff138216d6}\0000
service  : WinUSB
children : none - single function
ifaces   : {<generated-guid>}  [registry Device Parameters]
```

`pnputil /enum-drivers` names the package that got there, and its fingerprint is
route A rather than a class install: published name `oem237.inf`, original name
`zune.inf`, `Provider Name: libwdi`, driver version 6.1.7600.16385, signer
`USB\VID_045E&PID_063E (libwdi autogenerated)`.  A self-signed per-device package
is exactly what Zadig produces, and Windows 11 accepted it here with Secure Boot on.

1. `winusb.sys` is the devnode's function driver.  Windows 11 has no driver for
   `USB\MS_COMP_MTPZ`, which is why an unbound player has no driver at all rather
   than a wrong one, and why `libusb_get_device_list()` cannot contain it until
   something claims that compatible ID.
2. The devnode registers a device interface GUID, as `DeviceInterfaceGUIDs` or
   `DeviceInterfaceGUID` under its `Device Parameters` key.  Read it from the
   registry rather than from `DEVPKEY_Device_DeviceInterfaceGuids`: on the bound
   player that property came back empty while the registry value was there and
   libusb opened the device without complaint, which is why `check-driver.ps1`
   falls back to the key and prints where the GUID came from.

The second is not cosmetic, and it is the reason the obvious free route is not
enough.  In libusb 1.0.29 the WinUSB path in `libusb/os/windows_winusb.c` reads
those two values and returns `LIBUSB_ERROR_ACCESS` when neither exists: a player
bound to WinUSB without a registered GUID enumerates and still cannot be opened.

## Route A - Zadig

Zadig, by Pete Batard, upstream of libwdi: <https://zadig.akeo.ie>, or
`winget install akeo.ie.Zadig` - the Microsoft package repository carries the
upstream binary under the publisher `akeo.ie`, so there is nothing to build and
no INF to write.  Any recent build will do; 2.8 is the one the development machine
used, and where it kept the file is a fact about that machine rather than about yours.

Run it as administrator with the player attached:

1. Options, then enable **List All Devices** - the devnode has no driver, so
   without this the player is not offered.
2. Select the Zune (`VID_045E&PID_063E` on this machine, `VID_045E&PID_0710` for
   the Classic/Pad family).
3. Select **WinUSB** in the driver box - not libusbK, not libusb-win32, and not
   the generic/WCID install.
4. Install Driver, then unplug and replug.

Step 3 matters and is verified in upstream source rather than guessed: libwdi's
`libwdi/winusb.inf.in` has an `AddDeviceInterfaceGUID` section and a
`NoDeviceInterfaceGUID` one, and `libwdi.c` picks `NoDeviceInterfaceGUID` only
when `options->use_wcid_driver` is set.  A normal named WinUSB install therefore
registers the GUID that libusb needs; the generic WCID install does not.

If Windows refuses the package over signing, that is Windows' rule on third-party
packages, not something this app can code around.  libwdi self-signs, and the
community Zune installer documents the fix: reboot once with driver signature
enforcement disabled (Shift + Restart, Troubleshoot, Advanced options, Startup
Settings, Restart, then F7), install, reboot normally.  The binding survives.
Unverified on this machine - note in the commit whether it was needed.

## Route B - the community Zune installer

<https://github.com/magicisinthehole/zune-winusb-driver-setup> wraps libwdi for
exactly these two device IDs (`aft-driver-setup.exe list | install | restore |
check`, with a driver backup under `%LOCALAPPDATA%`) and is part of the
Android-File-Transfer-for-Linux Windows port.  That is the closest thing to a
ready-made Zune driver tool.  It is a third-party executable: it has not been
vetted or run here, and it is not a Zuuned release dependency.  Building it from
source is documented in that repository if you would rather not download a binary.

## Route C - Device Manager alone is not enough

Microsoft documents loading WinUSB through the class picker: Update driver,
Browse my computer, Let me pick from a list, **Universal Serial Bus devices**,
**WinUsb Device**.  That installs the in-box driver and no package at all, which
is why it is tempting - and it registers no device interface GUID, so per the
section above the app still cannot open the player afterwards.  If you end up
here, add the GUID as administrator and replug:

```
reg add "HKLM\SYSTEM\CurrentControlSet\Enum\USB\VID_045E&PID_063E\<serial>\Device Parameters" /v DeviceInterfaceGUIDs /t REG_MULTI_SZ /d "{<your-guid>}" /f
```

Generate the GUID with `powershell -NoProfile -Command "[guid]::NewGuid().Guid"`.
This is also the only route whose package is signed by Microsoft, so it is the one
to prefer if Secure Boot refuses Zadig's self-signed package.

## Verifying, in this order

1. `powershell -NoProfile -File packaging\windows\check-driver.ps1` - expect
   `status   : OK  problem=CM_PROB_NONE`, a `driver` line plus `service  : WinUSB`,
   and an `ifaces` line naming a GUID.  Read-only script: it installs nothing and
   needs no elevation.  Both runs above are its literal output.  A `service` naming
   `wudfwpdmtp` rather than `WinUSB` is not a failure - see the first section.
2. `build\devicetool.exe` - expect `libusb_sighted=1` and `VERDICT=agree`, which is
   what this machine answers now.  It opens no handle by design, so it proves
   reachability only, never MTPZ auth.
3. `build\zuuned.exe` - breach and the ZMDB library read now run on Windows: the
   player answers `GetDeviceInfo`, reports itself as Pavo (Zune HD), and 183 tracks
   arrive.  MTPZ authentication does **not**, because a development checkout carries
   no credentials - the log states `MTPZ authentication will fail` and the read
   happens anyway, so treat that step as unproven until a credentialed build exists
   (`docs/BUILD_WITH_MTPZ.md`).  `zunetool` is built by libzune's POSIX Makefile and
   is not part of the Windows build, so the application is the protocol test vehicle
   until a Windows probe target exists.  A failure at this step is a protocol or
   driver question, not an enumeration question - keep the log.

## What Windows cannot do that Linux can

Record this before a test so a Windows failure is not filed as a libzune bug.

- **Reset is a formality, not a recovery.**  WinUSB does answer
  `libusb_reset_device()`, and it answers with success - but that success is not a bus
  reset.  Measured 2026-10-21 on a wedged Zune HD: the player came back on the same bus
  address, `libusb_clear_halt()` on both endpoints answered success,
  `libusb_set_configuration(1)` answered success six times, and the bulk OUT pipe timed
  out through all of it (`libzune/docs/WINUSB_QUIRKS.md`).  So `zune_breach()`'s
  auto-reset-and-retry after an OpenSession wedge cannot recover here; it now prints
  what the reset returned and its error names the workaround, which is physical -
  unplug and replug, or hold the power button.  On Linux the same wedge is a
  `usbreset 045e:0710` away.
- **Nothing to detach.**  `libusb_kernel_driver_active()` returns
  `LIBUSB_ERROR_NOT_SUPPORTED` on Windows, so libzune's detach step is skipped.
  Correct, not a bug.
- **No udev counterpart.**  `packaging/68-zuuned.rules` keeps gvfs-mtp and libmtp
  off the device and grants the session access to the node.  Being the function
  driver answers both on Windows.  Do keep the Zune software absent.

## Backing out

Device Manager, the Zune entry, Update driver, and pick something else, or uninstall the
package's published `.inf` from the driver store (`pnputil /enum-drivers` to find
it).  After a replug the player returns to problem 28, because nothing in Windows
claims `USB\MS_COMP_MTPZ`.
